# SM8750 common support

Shared GICv3, 19.2 MHz timer, UFS/GCC and SMMU resources used by the OnePlus 13T PKX110 port. The initial extraction preserves the register operations from UniXNU-Pagani-Drivers `0d0b413de6b2caecf2f3128bb70f345342190bcd`.

The DTSI also describes disabled Adreno 830 GPU, Gen8 GMU, GPUCC, separate GX power controller (`0x3d68024/8`) and GPU SMMU nodes. Their MMIO windows and GPU/GMU interrupts come from the PKX110 Android runtime DTB recorded in the device repository. The device DTS supplies its observed chip ID `0x44050001` and model `Adreno830v2`. These nodes provide resource inputs for an A830 backend; no GPU driver or clock/power sequence is enabled by this change.

`GpuProbe.h` provides a read-only GPUCC snapshot and conditional SMMU identification for the optional OnePlus 13T UEFI application. It requires CX on, collapse/reset deasserted and both AHB/SMMU branches enabled and running before accessing the SMMU. Register facts come from [OnePlus gpucc-sun.c](https://github.com/OnePlusOSS/android_kernel_oneplus_sm8750/blob/745702d5ed2c0435f2b1d3bb78bc4f48422d4191/drivers/clk/qcom/gpucc-sun.c); SMMU offsets follow `drivers/iommu/arm/arm-smmu/arm-smmu.h` at that revision. Its transport has no write callback. It takes no power/clock ownership and cannot guarantee that firmware retains the sampled state. Run `cc -std=c11 -Wall -Wextra -Werror -fsanitize=address,undefined kits/Sm8750Platform/Test/gpu-probe.c -o /tmp/gpu-probe-test` and `ASAN_OPTIONS=detect_leaks=0 /tmp/gpu-probe-test` from this repository. The 128-state policy and failure tests pass; hardware access remains untested.

`Sm8750Gmu.c` implements the A830v2 firmware loader, cold HFI startup, bounded OOB and performance requests. `Sm8750GpuPower.c` configures the SM8750 clocks and CX domain after a caller-owned rail vote; `Sm8750GpuZap.c` performs secure CX initialization and PAS authentication for signed ZAP data. `Sm8750GmuCommandDb.c` parses bounded rail/BCM inputs, and `Sm8750SocInfo.c` reads the version-12 global SMEM headers and SoC/SKU fields directly through volatile accesses, skipping unrelated partition data. The 13T Run 68 whole-SMEM copy aborted at physical `0x81d9e000`; protected-gap host tests cover the selective parser, and Run 69 passed production compilation and prelink with this fix. The user confirmed that its temporary boot reached the system with roughly one visible frame update per second, clearing the prior SMEM panic for this boot. GPU initialization and rendering remain unverified. The OnePlus 13T `PaganiGpu.cpp` connects these operations to XNU memory, GPU/GMU SMMU contexts and the A830 command path.

The GMU implementation derives from the BSD-2-Clause-Patent SM8550 source at `23b2049fcd9e30356161def84231334fb55ecca9`; generation-specific register facts come from Linux `65ba8f34ec886ec72b2c07ddc8cf3d815c32869d` and the pinned OnePlus clock source. RSC/PDC ownership remains with AOP. Portable tests cover firmware data, stale/fatal status, HFI rejection, OOB/DCVS responses, SCM retries, clock timeouts, SMEM parsing and injected MMIO failures. The device's `build-gmu.py` builds an arm64/iOS 17 archive. The connected XNU driver has passed production compilation and kernel prelink. Run 74 subsequently stopped at the critical CXO AON clock write before GMU startup. The candidate matches the vendor write/delay/skip policy and keeps checked clocks, PLL/RCG/GDSC waits and later GMU/CP verification. A non-latching critical-enable model reproduces the old failure and passes the correction; Run 75 passed the complete kernel/Metal build and its paired image was accepted by fastboot for a temporary boot; Run 75 device readings advanced to DEMET at GPUCC +0x9010, reporting -110 with value 0x08000000 before GMU startup. The next candidate matches vendor branch2 HALT/FSM acknowledgement without enable-bit readback. Reported-value and NoC-ON regressions pass while actual halted clocks still time out; Run 76 passed the complete production kernel/Metal build and was downloaded with matching kernel hash and Data UUID. A later user-authorized temporary boot reached SMMU initialization with power stage 7; GMU startup remains unverified. Board policy currently retains high shared rail/bus votes and disables retention transitions; it does not qualify thermal or power management.

`PeripheralIO.h` adds bounded SPMI v7 observer reads, QUP1 S4 clock adoption, checked SPI delay programming and DSI command-FIFO writes. Board pin numbers, PMIC peripherals, panel limits and physical mappings remain in the device profile. The portable peripheral tests exercise these operations with register models; no new hardware result is claimed. Clock adoption requires boot firmware microcode, and DSI commands preserve existing scanout timing.

`Rpmh.h` resolves exact VRM names from the bounded command database and submits voltage/mode/enable requests through an idle apps DRV-2 ACTIVE TCS. Its shared write helper also accepts validated ARC and BCM commands for the GPU startup path. It checks register readback and all command acknowledgements, preserves other TCSes/IRQ bits and retains a timed-out slot without reuse. The caller supplies the board resource names and voltages and serializes requests. RSC v2/v3 layouts are supported; unknown layouts or non-idle slots are refused. Host fault models pass; rail voltage and boot behavior still require device validation.

`SmmuTakeover.h` also accepts a caller-supplied MMIO extent so QUP SE DMA can reuse its checked, exclusive VA64 bypass planner. Existing UFS defaults and firmware takeover rules remain unchanged. QUP mappings receive no firmware-bank exception; conflicting streams are reported without writes. Tests cover QUP/UFS coexistence and insufficient mapping extents in both existing build configurations.

Hardware addresses originate from the device's captured Android live DTB and the register definitions pinned in `soc.toml`. The CPU nodes describe affinities `0, 0x100, 0x200, 0x300, 0x400, 0x500, 0x10000, 0x10100` and the PSCI SMC conduit. All nodes remain disabled until the board enables them. The selected XNU SMP patch admits eight CPUs in two clusters, uses Aff1 for the core and Aff2 for the cluster, and preserves Aff2 in CPU lookup and reset entry. `NO_CPU_OVRD=1` excludes Apple-only interrupt override registers when cluster support is enabled. This is a source candidate; eight-core timer/IPI operation remains unverified on hardware. UFS and SMMU operations retain their C interfaces. Board partition names, memory windows, display and firmware policy remain in the device repository.

The selected Clutch scheduler uses one processor set for all eight CPUs. Its stock steal callback assumes one cluster and returns without releasing the caller's pset lock; two psets trigger a recursive lock panic when `thread_select()` reacquires that lock. Disabling Clutch's `multiple_psets_enabled` uses the existing `pset_create()` policy gate while retaining both hardware cluster IDs and all CPU affinities. The device regression reproduces the old double lock and checks the shared-pset policy against the selected XNU functions. Cluster-aware scheduling requires a separate Edge adaptation; this policy does not establish eight-core hardware stability.

Select this repository as `soc:sm8750` and `Sm8750Platform` in the main catalog. From the main checkout run `./unixnu defconfig oneplus13t_defconfig -D ../UniXNU-Pagani_SM8750`, `./unixnu fetch`, `./unixnu tree`, then the device README's checks and build commands. Use `--local-module soc:sm8750=../UniXNU-sm8750-common` while developing.

The original implementation reached the iPadOS UI on OnePlus 13T with build 39. This extracted profile needs a fresh hardware boot; it does not establish support for another SM8750 board. See the [device record](https://github.com/IssacL04/UniXNU-Pagani_SM8750/blob/main/porting.toml) and [SoC guide](https://unixnu.com/porting/soc-support).

Run 76 was later temporarily booted with user authorization. Device feedback reached SMMU initialization with power step 7, so the branch-clock correction passed its startup sequence on that boot. SMMU preparation returned a generic failure before GMU startup; this does not qualify GPU rendering or power management.

`Sm8750GpuSmmuPrepare` plans GPU SID 0/1 and GMU SID 5 routes while their masters remain reset. It preserves live firmware routes, reserves banks 0/1 for the GPU per the pinned OnePlus allocator, and selects the GMU bank from disabled, unreferenced banks starting at 2. It faults only invalid slots after a complete preflight and recheck. Geometry/global-state, masked overlap, EXIDS, resource exhaustion and all I/O failure tests run through the device's `scripts/test-gpu-smmu.py`. This passed the Run 78 production kernel build and local image checks; the Run 78 image was later sent through an authorized temporary fastboot boot; the user then reported Metal registered with rc=0, submissions/completions 1039/1039 and GPU presentation 518/0. This confirms that SMMU, GMU, CP self-tests and publication passed on that boot; controlled shader correctness, measured performance and runtime power transitions remain unqualified.

The current OnePlus 13T GPU candidate selects the board's 525 MHz OPP with its matched HFI voltage/dependency and bandwidth votes. Software tests cover all six captured speed-bin policies; achieved clock rate and thermal stability need device testing.

The 2026-11-04 candidate imports the peripheral resources and checked MMIO helpers from [Shad0w23333/UniXNU-OnePlus13T at 3c514bc](https://github.com/Shad0w23333/UniXNU-OnePlus13T/tree/3c514bc). Battery, audio, Bluetooth and camera resources are available to their board-selected drivers. Runtime operation on this integration remains unverified.
